# S-Tier Eats 3.1 — Notifications & Frequency Plan

## Problem this solves
Ranking is a **one-time setup task**: a user dumps in the spots they already have
opinions on, then has no reason to return. We need **recurring reasons to open the
app**. More restaurants does NOT fix this (that's an acquisition lever, not a
frequency lever — we already have 4,703). The fix is a notifications system that
surfaces things that *change between sessions*: new openings, friends' activity,
trending community picks, and a weekly nudge to use the decision features.

## Design principles (non-negotiable)
- **Every notification is a real event**, opt-in, and under a hard frequency cap. No
  spam, no fake "we miss you" filler. (feedback: build it properly.)
- **Permission prompt AFTER a value moment**, never on first launch. Trigger the soft
  pre-prompt after the user ranks their 3rd spot, creates a list, or invites a friend.
  Explain the value in a custom sheet first, THEN the system prompt (so a "no" to the
  soft prompt doesn't burn the one real iOS ask).
- **Global off + per-type toggles** in Settings → Notifications.
- **Frequency cap:** at most 1 push/day and ~2–3/week, coalesced by priority.
- **No restaurant-side anything** (standing rule). Notifications are a free consumer
  feature, never gated behind Plus.
- iOS/Android parity, iOS first (same pattern as 3.0).

---

## Phase A — Local notifications (NO backend, ships in 3.1)
On-device scheduling only: iOS `UNUserNotificationCenter` (UNCalendarNotificationTrigger /
UNTimeIntervalNotificationTrigger), Android `WorkManager` + `NotificationManagerCompat`.
No server, no FCM, no Cloud Functions. This phase delivers most of the frequency value
and the user's explicit Night Out ask. Reschedule all repeating notifications on each
app launch (iOS drops pending ones past a limit; keep them fresh).

### A1. Weekly "Night Out" reminder  ← the explicit ask
- Fires **weekly, default Thursday 4:30pm local** (pre-weekend dinner planning window).
- Copy: *"Where to tonight? Plan a night out from your S & A tiers."*
- Deep link: `stier://nightout` → opens NightOutView / "Plan a Night Out" directly.
- Impl: repeating `UNCalendarNotificationTrigger(weekday:5, hour:16, minute:30)`.
  Add a "Reminder day/time" picker in Settings later; ship with the default first.
- Only meaningful if the user has ≥3 ranked spots (otherwise Night Out is thin) — gate
  scheduling on that, or soften copy to "Build your tiers, then plan a night out."

### A2. New-openings nudge (catalog-diff, local — no backend)
- `Restaurants.json` is bundled and grows with each app update. Persist the set of
  **seen restaurant IDs** (UserDefaults / a small file). On launch after an update,
  diff the bundled catalog against the seen set.
- If N new IDs: schedule a local notif (next day ~11am): *"N new spots just landed in
  The Woodlands — rank them."* Deep link `stier://new` → Browse filtered to the new IDs.
- Update the seen set only after the notif is scheduled (so a user who never opens still
  gets the next batch merged). This is the "new openings" frequency lever with zero infra
  — it rides our existing catalog-update cadence.

### A3. Weekly "rank where you ate" prompt
- **Weekly, default Sunday 6pm:** *"Been out this week? Add it to your tiers."* Deep link
  to Browse/search. Feeds the ranking + visited loop.
- **Suppress if** the user ranked anything in the last 3 days (don't nag active users).

### A4. Lapsed re-engagement
- If the app hasn't been opened in **10 days**, schedule: *"The Woodlands food scene moved
  while you were gone — see what's trending."* Deep link `stier://community`.
- Track `lastActiveAt` locally; reschedule the 10-day timer on every launch so it only
  fires for genuinely lapsed users.

### Permission + Settings (Phase A foundation)
- Soft pre-prompt sheet after a value moment → system `requestAuthorization`. Consider iOS
  **provisional authorization** for the lower-stakes ones (A3/A4) so they deliver quietly
  to Notification Center without a hard opt-in.
- **Settings → Notifications:** master toggle + per-type toggles (Night Out, New spots,
  Weekly check-in, Trending/lapsed). Store in AppStorage; optionally mirror to
  `profiles/{effectiveUserID}.notifPrefs` so Phase B can honor them server-side.
- Central `NotificationScheduler` that owns all scheduling, the frequency cap (don't stack
  two in one day; priority: Night Out > New spots > weekly > lapsed), and reschedule-on-launch.

## Phase B — Push notifications (FCM + Cloud Functions, 3.2)
Needed only for events triggered by **other users** or server-side freshness. This is the
first Firebase Cloud Functions deploy for the project (we currently deploy only firestore
rules). Bigger lift — do it as 3.2 after Phase A proves the opt-in funnel.

### Infra
- Add **FCM** to both apps. iOS: upload APNs auth key to Firebase, implement the
  `UNUserNotificationCenter` + `MessagingDelegate`, register the FCM token and store it on
  `profiles/{effectiveUserID}.fcmTokens[]` (array — a user has multiple devices). Android:
  FCM is already available via Firebase; same token storage.
- **Firebase Cloud Functions** (Node) triggered on Firestore writes + a scheduled job.
  `firebase deploy --only functions`. Honor each recipient's `notifPrefs` + frequency cap
  server-side (store `lastPushAt` per user).

### B1. Friend-activity push (the real social frequency driver)
- Trigger: `onWrite` of a `placements/*` doc landing in **S tier** (limit to S, maybe A, to
  cap volume). Function resolves the actor's **followers**, filters to those with the
  friend-activity pref + an FCM token + not the actor, sends *"Jordan put Amrina in S."*
- **Requires a followers index.** `friendLists/{uid}` stores who *uid follows*; we need the
  inverse. Maintain a `followers` array (or a `followers/{uid}/{followerUid}` subcollection)
  written at follow/unfollow time, OR query. Spec the reverse index as part of B1.
- Caps: per-actor-per-day limit so a power-ranker doesn't spam their followers.

### B2. Weekly community digest push
- **Scheduled Function** (pub/sub cron, e.g. Friday 10am): compute the week's top mover /
  newly-crowned S from **consensus** deltas, send to opted-in users. Needs a weekly
  snapshot of `consensus` to diff against (store `consensusWeekly/{weekId}`).
- In Phase A this is approximated by A4's "see what's trending" local nudge.

### B3. Server-authoritative new openings
- Only if/when the catalog goes server-driven. For 3.1/3.2, A2 (local catalog-diff) covers
  it. Noted as future.

## Deep links to add (extend existing MainActivity / AppNav handlers; `stier://tier/<uid>` already works)
- `stier://nightout` → Plan a Night Out
- `stier://new`      → Browse filtered to new / unranked-near-me
- `stier://community` (or `stier://trending`) → community board

## Guardrails / analytics
- Log each notif **sent + opened** per type (local counter or a Firestore counter) to see
  which actually drive opens — kill the ones that don't after a few weeks.
- Hard global off, honor system DND, respect per-type prefs everywhere.

---

## Recommended build order
1. **A1 (Night Out weekly) + permission plumbing + Settings → Notifications screen** —
   ships the explicit ask and the opt-in foundation. Smallest, highest-visible.
2. **A2 (new-openings catalog-diff) + A3 + A4.**  ← completes Phase A / 3.1
3. **Phase B (FCM + Functions) friend-activity push** as 3.2 — the social driver.

## Automation & release (Store Ops aligned — `playbooks/store-ops.md`)
Everything below ships through the automated pipeline the recent apps use. Registry entry
already exists: `store_ops_apps.json` → `{slug: stier-eats, asc_id: 6773501518,
play_package: com.compofelice.stiereats}`. Repos: **iOS `Compo-CF/woodlands-eats`**,
**Android `Compo-CF/s-tier-eats-android`** (the latter is already in the keyless-Play
allowed-repos list).

### ⚠️ Prerequisite — iOS is NOT on the automated pipeline yet (close this first)
`woodlands-eats/.github/workflows/` has only **`ios-build.yml`**, which builds for the
**simulator with no code signing and no upload**. The portfolio standard (set 2026-11-16)
is a signed `ios-release.yml` on a GitHub macOS runner that archives + uploads to
TestFlight via the ASC API key. **Add `ios-release.yml` to `woodlands-eats`** (copy the
pattern from ghostline/neatly; XcodeGen project, ASC API key `6Q7XLL6CHU`, commit-count
build number) so iOS can ship hands-off like the rest. Until then S-Tier Eats iOS still
builds on MacInCloud (manual) — that's the one real automation gap for this app.

### Build (Level A — unattended once the iOS workflow exists)
- **Android:** `gh workflow run android.yml -R Compo-CF/s-tier-eats-android -f play_track=internal`
  (keyless CI build → signed AAB → Play internal track). Promote internal→alpha is Level B.
- **iOS:** `gh workflow run ios-release.yml -R Compo-CF/woodlands-eats -f upload=yes` (after the
  prerequisite above). Bump the marketing version first if the live one matches.

### Metadata + submit (ASC API — no Console)
- Version record + **What's New** + promo text for 3.1: draftable unattended (Level A) via the
  `~/appstoreconnect/` ASC scripts. Notifications add **no new IAPs/subs**, so no `asc_iap.py`
  and no first-price-commit trap.
- **Submit** after Anthony's on-device check: record the approval line in
  `store-ops/approvals.md`, then the daily task runs
  `submit_version.py --app 6773501518 --version 3.1 --build <N> --submit` (Level B).

### Backend deploys (scripted, keyless)
- Firestore rules (if touched for `notifPrefs`/`fcmTokens`): `firebase deploy --only firestore:rules`
  (already a one-command path in this repo — `firebase.json` + `.firebaserc`).
- **Phase B Cloud Functions:** `firebase deploy --only functions`; wire it into a GitHub Action on
  the repo so function deploys are CI-driven, not local. The scheduled digest + friend-activity
  functions then run **fully unattended** (pub/sub cron + Firestore triggers) — the recurring
  notification *content is auto-generated from data*, never hand-written each week. Phase A's copy
  is static templates with interpolated values (`N`, restaurant name), so it needs zero ongoing ops.

### What stays manual (hard limits — can't be automated)
- **Device check:** confirming notifications actually deliver and the deep links land on real
  hardware is Anthony's (a feel/hardware check, same class as GPS/purchase checks).
- **APNs auth key upload** to Firebase for FCM (Phase B): Console-only, one-time.
- Any **notification-related App Privacy** nutrition-label change: Console-only (ASC API can't touch
  `appDataUsages`).

## Not a substitute for the free levers (do in parallel)
- **Announce 3.0's social features** — the friend/Taste-Match loop can't drive returns if
  nobody knows it exists. Still unannounced.
- **Cross-channel weekly re-engagement** via the Dispatch newsletter (3,287 subs) + WAFWA
  group (~15.7K): a weekly "Woodlands food this week" that links back into the app. Zero
  app cost, complements the in-app notifications.
